# AlphaZero and MuZero Literature Notes

This note summarizes the AlphaGo Zero, AlphaZero, MuZero, ELF OpenGo, OpenSpiel,
Minigo, and KataGo literature from an implementation perspective. The focus is
what matters for this repository: Go under Tromp-Taylor-style rules, no human
game supervision, self-play data generation, MCTS search targets, modular game
interfaces, argmax-only deployment, and training reports.

## Short Answer

Yes, AlphaZero-style Go can be trained without human game data. The important
detail is that "no human data" does not mean "no supervised losses." The network
is trained with supervised objectives, but the labels are generated by the
agent itself:

- policy labels are MCTS visit-count distributions from self-play positions;
- value labels are final game outcomes from self-play;
- optional score and ownership labels are derived from the final board under the
  rules, not from human moves.

In the canonical loop, the first useful signal comes from scale plus search:
many self-play games, enough MCTS simulations, root exploration noise, replay,
symmetry augmentation, and repeated policy improvement. A randomly initialized
network is weak, but MCTS still produces a slightly different policy from the raw
network. The final winner gives a sparse but real reward. With enough games, that
small asymmetry is amplified.

For small-compute experiments, this is the painful part. If MCTS simulations are
very shallow and the self-play budget is tiny, the network may learn a policy
that is internally self-consistent but bad against uniform random. Canonical
systems solved this mostly with compute. KataGo solved much of it with better
targets and Go-specific efficiency tricks.

## How Learning Normally Starts

The normal AlphaZero mechanism is approximate policy iteration:

1. Start with random network weights.
2. For each self-play move, run MCTS using the current network for move priors
   and leaf values.
3. Sample or choose a move from the MCTS visit distribution.
4. Store the position and the normalized visit counts.
5. Finish the game and score it.
6. Train the policy head to match the MCTS distribution.
7. Train the value head to match the final outcome.
8. Repeat with newer checkpoints.

The raw network is not expected to be good at the start. The search policy is
the policy improvement operator. In the early phase, improvement can be weak and
noisy, but the loop is valid as long as games terminate, rewards are assigned
correctly, exploration covers enough actions, and the learner sees enough data.

The usual stabilizers are:

- large numbers of self-play games;
- hundreds or thousands of MCTS simulations per move;
- Dirichlet noise at the root during self-play;
- temperature early in the game and lower temperature later;
- a replay buffer spanning recent checkpoints;
- evaluation against earlier checkpoints and fixed baselines;
- residual convolutional networks with shared policy-value trunks;
- symmetry augmentation for Go;
- legal-move masking in search and training;
- strict rule handling for captures, suicide, ko or superko, pass, terminal
  scoring, and komi.

This is why a tiny local loop can fail even when the algorithm is conceptually
correct. If the search target is almost random, the network learns almost random
behavior. If games are truncated in a biased way, the value target can point in
the wrong direction.

## What "No Supervised Learning" Means

AlphaZero is not trained on human moves, expert games, opening books, or
handcrafted evaluation functions. It does train with supervised losses over
self-generated targets.

That distinction matters:

- Not allowed under the project goal: fitting policy logits to human SGF moves.
- Allowed: fitting policy logits to MCTS visit counts generated by self-play.
- Allowed: fitting value to win/loss from a completed self-play game.
- Allowed: fitting score or ownership to rule-derived final board quantities.
- Risky but sometimes pragmatic: using a hand-designed tactical evaluator as a
  temporary search teacher. That is not canonical AlphaZero. If used, it should
  be documented as a bootstrap and phased out once neural MCTS is stable.

KataGo is the best precedent for adding richer Go-specific targets while staying
self-play based. It still learns from neural-net-guided MCTS self-play, but adds
auxiliary outputs such as score and ownership to improve sample efficiency.

## Policy And Value Networks

In the modern Go line, policy and value are normally two heads on one shared
network.

AlphaGo Zero used one neural network `f_theta(s) = (p, v)`, with a shared
residual convolutional trunk, a policy head, and a value head. AlphaZero kept the
same basic idea. KataGo extends the head set with additional policy, value,
score, and ownership-related predictions, but still uses a shared trunk.

For this repo, the default Go model should therefore be:

- shared spatial trunk;
- policy head over `board_size * board_size + pass`;
- value head from the current player's perspective;
- optional ownership head over board points;
- optional score head or score-distribution head later.

An MLP is useful as a smoke-test baseline, but Go strongly rewards spatial
inductive bias. A residual convolutional network is the standard starting point.

## AlphaGo Zero

Primary source:

- [Silver et al. 2017, Mastering the game of Go without human knowledge](https://www.nature.com/articles/nature24270)

Core points:

- Go only.
- No human games.
- Uses only the rules of Go.
- Uses a single policy-value network.
- Uses MCTS guided by network priors and network values.
- Does not use random rollouts in the AlphaGo Zero search.
- Trains policy from MCTS visit counts.
- Trains value from the final game winner.
- Uses a residual convolutional network.
- Uses board-history feature planes.
- Uses Go board symmetries.

Implementation details that matter:

- MCTS is not merely an inference add-on. It is the mechanism that generates the
  improved policy target.
- Self-play uses exploration. Evaluation and final play are more deterministic.
- The training target for a position is from the player-to-move perspective.
- Go is scored at the end using rules and komi.
- A game needs robust termination. Passes and maximum-length handling must not
  create biased rewards.

Repository implication:

For a faithful implementation, our training loop should produce samples like
`(observation, legal_mask, mcts_visit_policy, final_outcome)` and the network
should be trained to predict the search policy and outcome from the same player
perspective used by MCTS.

## AlphaZero

Primary source:

- [Silver et al. 2017, Mastering Chess and Shogi by Self-Play with a General Reinforcement Learning Algorithm](https://arxiv.org/abs/1712.01815)

Core points:

- Generalizes AlphaGo Zero to chess, shogi, and Go.
- Starts from random play.
- Uses no domain knowledge beyond game rules.
- Uses MCTS for policy improvement.
- Uses one policy-value network.
- Uses game-specific legal move generation and terminal scoring.
- Removes more Go-specific engineering than AlphaGo Zero.

Typical AlphaZero training system:

- actors generate self-play games with MCTS;
- a learner samples from replay and updates the network;
- evaluators compare checkpoints to fixed baselines or older checkpoints;
- checkpoints are promoted based on evaluation;
- metrics and analysis logs are stored continuously.

Repository implication:

This project should keep the current modular split:

- `games`: rules, observations, legal actions, terminal scoring;
- `az`: MCTS, self-play, replay, training, evaluation;
- `models`: policy-value networks;
- `agents`: deployment-time action selection;
- `apps`: Streamlit or HTML play surfaces;
- `reporting`: metrics, plots, and run summaries.

For deployment, argmax over legal policy logits is acceptable if that is the
explicit product goal. For training, MCTS remains the standard way to improve the
targets.

## MuZero

Primary sources:

- [Schrittwieser et al. 2019, Mastering Atari, Go, Chess and Shogi by Planning with a Learned Model](https://arxiv.org/abs/1911.08265)
- [Nature version](https://www.nature.com/articles/s41586-020-03051-4)

Core points:

- Does not need access to the true game dynamics during planning.
- Learns a latent model for planning.
- Predicts reward, policy, and value from latent states.
- Uses tree search in latent space.
- Matches AlphaZero-level board-game performance while also working on Atari.

MuZero has three major functions:

- representation: observation to latent state;
- dynamics: latent state plus action to next latent state and reward;
- prediction: latent state to policy and value.

Repository implication:

MuZero is not the right first implementation for Go because we already have an
exact Go simulator. AlphaZero is simpler, easier to debug, and better aligned
with modular game rules. MuZero becomes interesting later for games where a
learned model is useful: imperfect information, stochastic transitions, hidden
state, expensive simulators, or non-board environments.

## OpenSpiel AlphaZero

Primary source:

- [OpenSpiel AlphaZero documentation](https://openspiel.readthedocs.io/en/latest/alpha_zero.html)

Useful design pattern:

- actors produce trajectories through self-play;
- MCTS evaluators can use either random rollouts or neural network priors and
  values;
- the learner stores trajectories in a fixed-size FIFO replay buffer;
- evaluators run separately from actors and learner;
- checkpoints and JSONL logs are written to the run directory;
- analysis utilities plot losses, value accuracy, evaluation results, actor
  speed, and game lengths.

Repository implication:

Our single-process loop is fine as a scaffold, but serious runs should move
toward this architecture:

- multiple self-play workers;
- batched neural inference;
- a replay queue or on-disk replay shards;
- a learner process;
- evaluator jobs;
- checkpoint promotion;
- machine-readable metrics plus a markdown report.

## Minigo

Primary source:

- [tensorflow/minigo](https://github.com/tensorflow/minigo)

Useful design pattern:

- open AlphaGo Zero-style Go implementation;
- separate self-play, training, validation, and checkpoint workflows;
- uses held-out self-play data for validation;
- treats training runs as artifacts rather than one-off scripts.

Repository implication:

For this repo, each model run should produce:

- config snapshot;
- metrics JSONL;
- checkpoints;
- best checkpoint;
- plots;
- markdown report;
- command used to reproduce the run.

## ELF OpenGo

Primary sources:

- [Tian et al. 2019, ELF OpenGo: An Analysis and Open Reimplementation of AlphaZero](https://arxiv.org/abs/1902.04522)
- [ICML proceedings PDF](https://proceedings.mlr.press/v97/tian19a/tian19a.pdf)

Core points:

- Open-source AlphaZero-style Go reimplementation.
- Demonstrated superhuman Go performance.
- Released code, models, self-play datasets, and analysis.
- Shows that faithful AlphaZero-style training works, but requires large-scale
  infrastructure and careful implementation.

Repository implication:

If a small run fails to beat random, that is not evidence that self-play cannot
work. It usually means the run is underpowered or the game/reward distribution
is broken. The first debugging questions should be:

- Are captures, suicide, ko/superko, passing, komi, and scoring correct?
- Are terminal rewards from the current player's perspective?
- Are legal masks enforced in MCTS, policy loss, and inference?
- Are games terminating naturally rather than by biased truncation?
- Are MCTS visit targets meaningfully better than uniform random?
- Is replay large and diverse enough?
- Is validation measuring the behavior we care about?

## KataGo

Primary sources:

- [Wu 2019, Accelerating Self-Play Learning in Go](https://arxiv.org/abs/1902.10565)
- [KataGo methods documentation](https://github.com/lightvector/KataGo/blob/master/docs/KataGoMethods.md)
- [Hugging Face paper page](https://huggingface.co/papers/1902.10565)

Core points:

- Still self-play and neural-net-guided MCTS.
- No human move supervision.
- Much more compute-efficient than plain AlphaZero-style Go training.
- Adds auxiliary targets and other implementation improvements.
- Important Go-specific heads include ownership and score-related predictions.

Why this matters for our problem:

Plain win/loss is a sparse target. On 19x19 Go, random or weak self-play can
produce long games where the final winner gives poor local credit assignment.
Ownership and score targets make every board point and final margin informative.
They are derived from the completed game under the rules, so they do not violate
the no-human-data constraint.

Repository implication:

Our current ownership head is directionally aligned with KataGo. The next useful
extensions are:

- board-history planes;
- score-margin or score-distribution head;
- stronger MCTS targets;
- better replay reuse;
- parallel self-play;
- checkpoint-vs-checkpoint evaluation;
- validation split by color, length, pass frequency, captures, and score margin.

## Tromp-Taylor Rules

Sources:

- [Tromp-Taylor rules](https://tromp.github.io/go.html)
- [Commentary on Tromp-Taylor rules](https://home.snafu.de/~jasiek/intro.html)

Tromp-Taylor is attractive for ML because it is compact and mechanically
scoreable:

- positions are black, white, or empty;
- stones without liberties are cleared;
- suicide is forbidden in the no-suicide variant;
- repeated positions are forbidden by positional superko;
- two consecutive passes end the game;
- score is area-style: stones plus controlled empty points, with komi applied to
  white.

Repository implication:

For this project, Go training and Streamlit play should use one consistent
ruleset. Captured intersections must become empty and immediately legal again
unless the move would violate suicide or superko. Scoring, ownership labels, and
validation outcomes should all use the same Tromp-Taylor implementation.

## Why Random Baselines Can Mislead

Uniform random legal play is not a standard AlphaZero promotion target. It is a
useful sanity check, but it can be biased by:

- komi;
- board size;
- max-move truncation;
- pass behavior;
- whether suicide is legal;
- whether random chooses pass too often;
- whether validation alternates colors;
- how truncated games are scored.

The literature usually evaluates by playing checkpoints against:

- previous versions;
- fixed search agents;
- established engines;
- final tournament opponents;
- sometimes raw-network versus search-enhanced versions.

For our goal, "near 100/100 against uniform random" is still useful because it
tests whether argmax-only inference has learned basic captures, territory, and
passing. It should be reported with:

- color split;
- board size;
- komi;
- max moves;
- pass action policy for the random agent;
- scoring rules;
- confidence interval or repeated seeds.

## Where Our Tactical Bootstrap Fits

A rules-only tactical evaluator is not the normal AlphaZero method. Canonical
AlphaZero uses the neural network as the MCTS evaluator and relies on final game
outcomes for value targets. OpenSpiel also describes standard MCTS where values
come from random rollouts and priors are uniform, but AlphaZero MCTS uses neural
priors and values.

A tactical evaluator can be justified as a bootstrap if we are explicit:

- it uses rules, not human games;
- it is a temporary search teacher, not the final agent;
- the deployed policy remains the neural network's argmax legal move;
- success must be revalidated when training transitions to neural MCTS;
- reports should mark whether targets came from neural, rollout, hybrid, or
  tactical MCTS.

This is closer to pragmatic expert iteration than pure AlphaGo Zero. It may be
reasonable for getting a small model off the ground on limited compute, but the
long-term target should be neural MCTS self-play with rule-derived score and
ownership auxiliaries.

## Recommended Training Plan For This Repo

Near term:

1. Keep Tromp-Taylor rules as the single Go ruleset.
2. Use the convolutional policy-value-ownership model as the default Go model.
3. Keep MLP only for tests and very small smoke runs.
4. Use MCTS visit counts as policy targets.
5. Use final outcome and score-derived targets for value.
6. Use ownership auxiliary loss for Go.
7. Use symmetry augmentation.
8. Report losses, validation win rate, self-play length, score margins, color
   split, and pass rate.
9. Validate argmax-only inference against uniform random legal play.
10. Also evaluate against previous checkpoints or small MCTS baselines.

Medium term:

1. Add board-history planes.
2. Add a score-margin or score-distribution head.
3. Add parallel self-play workers.
4. Batch model inference during MCTS.
5. Store replay to disk.
6. Add checkpoint promotion matches.
7. Add a pure neural-MCTS training recipe after tactical bootstrapping.
8. Add Hugging Face Hub model cards with run reports and exact commands.

For 19x19 specifically:

- expect much more data than 9x9;
- avoid biased max-move truncation;
- validate by color;
- use larger residual networks than the smoke model;
- prefer many self-play positions and stronger MCTS over many tiny iterations;
- treat 100 random games as a noisy smoke metric, not a full strength estimate.

## Practical Takeaways

- AlphaZero without human data is possible, but it is compute hungry.
- The policy and value heads are normally on the same shared network.
- The policy target is not the raw best move. It is the MCTS visit distribution.
- The value target is normally the final result from self-play.
- Score and ownership targets are the main KataGo-style way to make Go training
  more sample efficient without adding human data.
- A tactical rules evaluator is a bootstrap shortcut, not canonical AlphaZero.
- Our implementation should make the evaluator type visible in reports so runs
  are scientifically interpretable.
